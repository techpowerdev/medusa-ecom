เทียบ burst ตามเกณฑ์ AC-31 (`checkout-timing.js --compare`): median (a) ไม่มี burst / มี burst = 33,608 / 49,485 = **67.9%** → "ทั้งสอง" (OPS-20a ได้ 42.1% — runner ต่างเครื่อง ผลสัมบูรณ์แกว่งได้)

## ตีความ: ช่วงหลักของ AC-31 อธิบายด้วยความอิ่มตัวได้หรือไม่
1. **pool ของ knex ของ server เต็มตลอดช่วง checkout ทั้งสอง run** — `numUsed` = 10 ทุก sample (= ขนาด pool ค่าเริ่มต้น เพราะ `DATABASE_POOL_MAX` ว่างใน load run) และ `numPendingAcquires` median 673.5 (มี burst) / 319 (ไม่มี burst) ไม่เคยเป็น 0 เลยในช่วง checkout → ทุก query ของ route complete ต้องต่อคิวรอ connection; คิวของ run มี burst ยาวเป็นราว 2 เท่า ตรงกับ (b)/(d) ที่โตขึ้นราว 1.6–1.7 เท่า
2. **ฝั่ง Postgres ไม่อิ่มตัว** — CPU ของ postgres median 27–29%, `state = active` median 1, wait `Lock` p95 = 0 (มีพุ่งถึง 5–8 บางวินาที), connection ส่วนใหญ่เป็น `idle`/`idle in transaction` ที่รอ `Client` → connection ที่ถูกยืมออกจาก pool **ไม่ได้รอ DB** แต่รอฝั่ง Node ระหว่าง query (รวม transaction ที่เปิดค้าง — `idle in transaction` p95 7–7.6)
3. **CPU ของ server เกิน 1 core ตลอด** (median 116–118%, max 158–179%) ขณะที่ event-loop delay p95 ต่อวินาทีแค่ 27–39 ms (max ต่อวินาทีมีพุ่ง 111–184 ms) → event loop ไม่ได้ถูกบล็อกยาว แต่ process ทำงานเต็มกำลัง (ส่วนเกิน 100% คือ thread ของ GC/libuv) — ความอิ่มตัวคือ CPU + pool ไม่ใช่ event loop ค้าง
4. **(d) ของกลุ่ม ok (ช่วงหลัก)** = step ของ `completeCartWorkflow` หลัง hook (สร้าง order, ตัด inventory, payment) ที่ query หลายครั้งต่อ checkout → แต่ละ query รอคิว pool ที่ยาวหลายร้อย จึงอธิบายได้ด้วยความอิ่มตัวของ pool เป็นหลัก ประกอบกับ CPU ของ server ที่เต็ม (เวลาระหว่าง query ของ connection ที่ถือไว้ยาวขึ้น → pool คืนช้า)
5. **(e)** (median 3.2 s มี burst / 1.2 s ไม่มี burst) **อธิบายด้วย event-loop delay ไม่ได้** (p95 < 40 ms ต่อวินาที) — แต่ (e) รวม `authenticate` + ownership ของ cart ที่ query DB ก่อนถึง middleware ของ (b) จึงต้องรอคิว pool เดียวกัน (ประกอบกับคิว accept ของ CPU ที่เต็ม) — เครือข่ายใน runner ไม่น่าเป็นส่วนใหญ่ แต่ยังแยกเป็นตัวเลขไม่ได้ด้วยตัวชี้วัดของ AC-32
6. burst ทำให้ทุกช่วงโตพร้อมกัน (เหมือน OPS-20a ข้อ 2) สอดคล้องกับคิว pool ที่ยาวขึ้น (median 673.5 เทียบ 319) ขณะที่ CPU ของ server เท่าเดิม (116% เทียบ 118%) → ส่วนที่ burst เพิ่มคือ request ที่แย่ง connection ของ pool ไม่ใช่ CPU

ข้อสรุป: **checkout flash อิ่มตัวที่ server ทั้งสอง run** (เข้าเกณฑ์ CPU และ pool) — ช่วงหลัก (d) และ (e) อธิบายได้ด้วยการรอ pool ของ knex (ขนาด 10) เป็นหลัก ไม่ใช่ event loop ค้างและไม่ใช่ Postgres

## ข้อเสนอ (ไม่แก้ใน OPS-20b — ต้องเป็น ADR/task แยกพร้อม AC ตาม AC-32)
- task วัดผลต่อ (ไม่เพิ่ม infra): รัน load แบบเดียวกันโดยตั้ง `DATABASE_POOL_MAX` (env ของ OPS-2 ที่มีอยู่แล้วใน `docker-compose.prod.yml`) เช่น 20 / 40 แล้วเทียบ (a)–(e) + ตัวชี้วัดชุดนี้ — ดูว่าคิว pool หายแล้ว checkout เร็วขึ้นหรือ CPU ของ server กลายเป็นคอขวดเดี่ยว (ต้องคำนึง `max_connections` ของ Postgres เมื่อ server ≥ 2 replicas)
- วัดเวลาถือ connection/transaction ต่อ step ใน (d) (`idle in transaction` p95 7–8) เพื่อหาว่า step ไหนถือ connection ระหว่างทำงานฝั่ง Node
- prod: ค่า pool ต่อ replica เป็นการตัดสินใจเชิง capacity → ADR หลังได้ผลข้างบน
- ผลนี้ได้บน runner เดียวกับ k6 (Q-O3 a) — ยังไม่แทน production (staging = OPS-19 ⏸)
